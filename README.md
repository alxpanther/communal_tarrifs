# Utility Tariffs Automation Pipeline

Интеллектуальная система автоматического сбора, AI-сравнения, отправки отчетов в Telegram и публикации тарифов ЖКХ для Android-приложения.

Поддерживается страны бывшего СССР. У каждой страны свой конфиг (`config/<код>/`), свой пайплайн (`src/countries/<код>/fetcher.py`) и свой выходной файл `tariffs_<код>.json`; всё общее вынесено в `src/common/`. Рядом с файлами тарифов публикуется `tariffs_index.json` — список стран, которые вообще опубликованы: по нему приложение узнаёт о новой стране, не обновляясь.

## 🚀 Возможности
0. **Четыре категории тарифов:** электроэнергия, холодная вода + водоотведение, **горячая вода** и **централизованное отопление**. Каждая — отдельный top-level блок в JSON.
1. **Мульти-источниковый сбор:** Забор данных с референсных сайтов (все URLs конфигурируются в `config/ua/sources.json`, никаких зашитых строк в коде).
2. **AI-валидация и веб-поиск (Gemini Search Grounding):** Скрипт через Gemini анализирует альтернативные источники и проверяет даты вступления в силу тарифов (постановления НКРЕКП / Кабмина).
3. **Автоматическое динамическое определение актуальной модели Gemini:** Скрипт перед запуском вызывает `client.models.list()`, отбирает самые свежие доступные модели семейства Flash (например, `gemini-2.5-flash`, `gemini-3.6-flash` и т.д.) и сортирует их по номеру версии, избавляя вас от необходимости переписывать код при выходе новых версий моделей Google.
4. **Сравнение расхождений:** Если найдены новые тарифы или дата вступления в силу на сторонних сайтах позже референсных, формируется сводная таблица с указанием URLs и высылается в **Telegram**.
5. **Единообразные источники и Ручное переопределение (Manual Override):** Все блоки (`electricity`, `water`, `hot_water`, `heating`) используют единообразное имя поля `source_url`. Любое значение можно зафиксировать вручную, вплоть до добавления города, которого нет на сайте-источнике — см. раздел [Ручное переопределение](#-ручное-переопределение-тарифов-manual_override).
6. **Запуск и Деплой в Docker:** Сбор тарифов и деплой в Cloudflare R2 в 1 команду.
7. **Автоматический запуск 25-го числа каждого месяца:** Настроен крон в GitHub Actions.
8. **Двойной мульти-деплой (Cloudflare R2 + GitHub Pages):** Файлы `tariffs_<код>.json` и индекс `tariffs_index.json` публикуются сразу на Cloudflare R2 и GitHub Pages.
9. **Жёсткая валидация тарифов на воду:** Ответ модели сверяется с исходной таблицей — каждая тройка «водопостачання / водовідведення / разом» должна встречаться в источнике именно в таком порядке, количество строк обязано совпадать, одна и та же строка не может быть извлечена дважды. Если хоть что-то не сошлось, старые данные остаются нетронутыми, а в Telegram уходит перечень претензий.
10. **Текстовые поля берутся из источника, а не из ответа модели:** Тройка чисел служит ключом связи со строкой таблицы, после чего `supplier` и период действия подставляются из самого HTML. Модель регулярно «исправляет» непривычные украинские названия (`Словміськводоканал` → `Словмісьководоканал`), но в JSON попадает только написание с сайта.
11. **Стабильные `city_code` (`config/ua/city_registry.json`):** Идентификаторы городов не зависят от ответа модели — они хранятся в постоянном реестре и после первого назначения никогда не меняются. Android-приложение хранит `city_code` как выбор пользователя, поэтому его «дрейф» между запусками недопустим.
12. **Несколько стран за один прогон:** `src/run_country.py` прогоняет страны по очереди и в конце пересобирает индекс. Сбой одной страны не останавливает остальные: она остаётся с прежним опубликованным файлом, а в Telegram уходит алерт.
13. **Страны без источника для разбора:** у Армении и Азербайджана регулятор публикует решения текстом и в PDF, поэтому их числа целиком лежат в `config/<код>/sources.json` → `manual_override`, а общий пайплайн `src/common/manual_pipeline.py` делает из них такой же JSON.
14. **Горячая вода и отопление парсятся без LLM:** таблицы источника жёсткие (2–4 колонки), поэтому числа снимаются регулярками, а не моделью. Модель спрашивают только о названии города и только для поставщиков, которых ещё нет в реестре — в устоявшемся состоянии вызовов модели по этим блокам ноль.

## 🌍 Страны и индекс (`config/countries.json`)

Список публикуемых стран лежит в `config/countries.json` — это единственное место, где страна
объявляется. Пока записи там нет, страна не собирается и не публикуется.

```json
{
  "code": "AM",
  "country_names": { "ru": "Армения", "uk": "Вірменія" },
  "currency": "AMD",
  "pipeline": "am",
  "enabled": true,
  "min_app_version": ""
}
```

| Поле | Смысл |
|---|---|
| `code` | Код ISO 3166-1 alpha-2. В данных — в верхнем регистре, в путях и именах файлов — в нижнем. |
| `country_names` | Название страны по языкам интерфейса приложения. Попадает и в файл тарифов, и в индекс: по нему приложение показывает страну в выборе адреса **до** того, как скачает её тарифы. |
| `currency` | Код валюты ISO 4217. |
| `pipeline` | Имя папки в `src/countries/`, чей `fetcher.py` собирает эту страну. |
| `enabled` | `false` — страну не показывать в приложении и не запускать по умолчанию; файл при этом остаётся на месте. |
| `min_app_version` | Минимальная версия приложения (`1.4.0`), ниже которой страна не показывается. Пусто — ограничения нет. |

Там же, в `publication`, лежит раскладка публикации каждого хоста — из неё собираются обе копии
индекса:

* `docs/tariffs_index.json` — для GitHub Pages, пути плоские: `tariffs_am.json`;
* `dist/cloudflare/tariffs_index.json` — для Cloudflare R2, пути по папкам: `am/tariffs_am.json`.

Индекс пересобирается в конце каждого прогона `run_country.py` (или отдельно —
`python src/build_index.py`) и описывает только те страны, чей файл реально лежит на диске. Если не
удалось прочитать ни одного файла страны, индекс не переписывается вовсе: вчерашний индекс лучше
пустого. Полное описание формата и правил, которые применяет приложение, — в
[docs/ru/JSON_SPECIFICATION.md](docs/ru/JSON_SPECIFICATION.md), раздел 6.

## 🔒 Реестр городов (`config/ua/city_registry.json`)

Файл сопоставляет название поставщика с сайта-источника постоянному `city_code` и `city_name`. Две независимые секции, потому что водоканалы и теплоснабжающие предприятия — разные компании:

```json
{
  "suppliers": {
    "ПАТ АК \"Київводоканал\"": { "city_code": "kyiv", "city_name": "Київ" }
  },
  "heat_suppliers": {
    "КП \"КИЇВТЕПЛОЕНЕРГО\"": { "city_code": "kyiv", "city_name": "Київ" }
  }
}
```

* `suppliers` — водоканалы (блок `water`).
* `heat_suppliers` — поставщики тепла, **общая секция для `hot_water` и `heating`**, потому что горячую воду и отопление в городе поставляет одно и то же предприятие.

Правила работы:

* Реестр **обязан быть в git** — GitHub Actions коммитит его вместе с файлами тарифов. Без этого CI начнёт с пустого реестра и выдаст другие коды.
* Уже назначенный `city_code` скрипт не перезаписывает никогда, что бы ни вернула модель.
* Новый поставщик на сайте → код генерируется транслитерацией по постанові КМУ № 55 від 27.01.2010 (чистая функция на Python, не LLM), дописывается в реестр и уходит уведомление в Telegram.
* Поставщик пропал с сайта → запись остаётся в реестре, но выпадает из JSON; в Telegram уходит предупреждение, потому что у пользователей с этим `city_code` выбор перестанет работать.
* Коды можно править вручную — но только осознанно и вместе с миграцией в Android-приложении.

### Как назначается «простой» код города

Если в городе один поставщик, он получает чистый код (`vinnytsia`). Если несколько — чистый код достаётся главному, а остальные получают суффикс по своему названию:

* для **воды** главный тот, у кого в названии есть маркер водоканала (`водоканал`, `вувкг`, `водопостач`, …);
* для **тепла** — тот единственный, у кого в кавычках названия встречается корень названия города: `КП "КИЇВТЕПЛОЕНЕРГО"` → `kyiv`, а `ТОВ "Євро-Реконструкція" (Київ)` → `kyiv_yevro_rekonstruktsiia`.

Если подходящих кандидатов ноль или больше одного, чистый код не выдаётся никому и все получают суффиксы. Так вышло, например, с Дніпром, Миколаєвом, Черкасами и Черніговом: в блоках тепла там есть только `dnipro_teploenerho`, `dnipro_komenerhoservis` и т. п.

> ⚠️ **Важно для Android:** не считайте, что `city_code` из блока `water` обязательно найдётся в `hot_water` и `heating`. Совпадение гарантировано только там, где в городе один поставщик тепла. Для связывания услуг между собой используйте `city_name`, а `city_code` — как стабильный ключ выбора внутри конкретного блока.

Для деплоя файлов тарифов и индекса стран в ваш Cloudflare R2 бакет `kommeter` используйте сервисы Docker Compose. Раскладка на R2: `<код>/tariffs_<код>.json` для каждой страны и `tariffs_index.json` в корне бакета.

```bash
docker compose up --build
```

```bash
docker compose run --rm tariffs-deploy
```

### Вариант 1. Запуск через Docker (Рекомендуемый)

```bash
# Генерация файла тарифов
docker compose run --rm tariffs-fetcher

# Деплой в Cloudflare R2

```

---

### Вариант 2. Локальный запуск на Python

```bash
# 1. Установите зависимости
pip install -r requirements.txt

# 2. Запустите генерацию
python src/run_country.py          # все включённые страны, затем индекс
python src/run_country.py ua       # только одна страна
python src/run_country.py am az    # несколько стран
python src/build_index.py          # только пересобрать tariffs_index.json
```

`run_country.py` без аргументов берёт список стран из `config/countries.json` (все с `"enabled": true`) и в конце пересобирает обе копии `tariffs_index.json`.

---

### Вариант 3. Автоматический запуск через GitHub Actions

В файле `.github/workflows/fetch_tariffs.yml` настроено расписание:
- **Крон:** `0 11 25 * *` (каждое **25-е число месяца в 11:00 UTC**).
- **Все страны — одной задачей, последовательно.** Так два запуска не могут одновременно писать в ветку или деплоить Pages. Перед `git push` задача перебазируется на ветку и повторяет попытку, поэтому чужой коммит, появившийся во время прогона, её больше не роняет.
- **Мульти-деплой:** файлы публикуются сразу и на **Cloudflare R2** (`kommeter/<код>/tariffs_<код>.json` плюс `kommeter/tariffs_index.json`), и на **GitHub Pages**. Список загрузок в R2 берётся из сгенерированного индекса, а не прописан в workflow.
- Можно запустить вручную во вкладке **Actions $\rightarrow$ Fetch and Update Tariffs $\rightarrow$ Run workflow**; в поле **countries** можно перечислить коды стран через пробел (пусто = все).

## ⚙️ Управление источниками и моделями (`config/<код>/sources.json`)

У каждой страны свой файл: `config/ua/sources.json`, `config/am/sources.json`,
`config/az/sources.json`. Ниже — украинский, самый полный.

```json
{
  "settings": {
    "auto_select_latest_model": true,
    "gemini_model": "gemini-2.5-flash",
    "timeout_seconds": 15
  },
  "reference_sources": {
    "electricity": "https://tariffa.com.ua/ru/tarif-na-elektroenergiy",
    "water": "https://index.minfin.com.ua/ua/tariff/water/",
    "hot_water": "https://index.minfin.com.ua/ua/tariff/hotwater/",
    "heating": "https://index.minfin.com.ua/ua/tariff/heating/",
    "hot_water_kyiv": {
      "url": "https://index.minfin.com.ua/ua/tariff/kiev/hotwater/",
      "supplier": "КП \"КИЇВТЕПЛОЕНЕРГО\"",
      "city_name": "Київ",
      "effective_date": "2022-10-01",
      "decree_info": "Розпорядження КМВА № 673 від 30.09.2022, тариф для населення на період воєнного стану"
    }
  }
}
```

| Ключ | Обязателен | Что делает |
|---|---|---|
| `electricity` | да | Без него скрипт падает с фатальной ошибкой и пишет в Telegram. |
| `water` | да | То же самое. |
| `hot_water` | нет | Если ключа нет, блок `hot_water` просто переносится из прошлого JSON без изменений. |
| `heating` | нет | Аналогично. |
| `hot_water_kyiv` | нет | Отдельная страница для КП «Київтеплоенерго». Из HTML берётся **только число**, а `supplier`, `city_name`, `effective_date` и `decree_info` подставляются из этого же блока конфига. |

### Страны без сбора данных: блок `electricity.zones`

У Армении и Азербайджана сбора нет, поэтому в их `sources.json` есть ещё один ключ — `electricity`
с расписанием зон и коэффициентами:

```json
"electricity": {
  "unit": "kWh",
  "zones": {
    "two_zone": {
      "description": "Двухзонный тариф (День/Ночь)",
      "day":   { "hours": "07:00 - 23:00", "coefficient": 1.0 },
      "night": { "hours": "23:00 - 07:00", "coefficient": 0.79373 }
    }
  }
}
```

Ставка зоны нигде не записывается руками — она всегда считается как `base_rate × coefficient`, где
`base_rate` берётся из `manual_override.electricity.base_rate`. Так двухзонный и трёхзонный тарифы
не могут разойтись с базовым. Правка часов или коэффициента здесь доходит до опубликованного файла
на ближайшем запуске.

### Почему у Киева отдельный источник

Сводные таблицы minfin публикуют только тарифы, установленные **НКРЕКП**. У КП «Київтеплоенерго» тариф устанавливает КМДА, поэтому предприятия нет ни в таблице горячей воды, ни в таблице отопления. Горячая вода по нему берётся с отдельной страницы minfin по Киеву, а отопление — через `manual_override` (см. ниже), потому что на сайте КТЕ цифры лежат только в PNG-картинках и PDF.

## 🖐 Ручное переопределение тарифов (`manual_override`)

### Где

Файл **`config/<код>/sources.json`** нужной страны, ключ верхнего уровня `manual_override`. Больше нигде тарифы руками не правятся: `docs/tariffs_<код>.json` и `assets/tariffs_<код>_default.json` перезаписываются скриптом при каждом запуске, и любая правка в них будет затёрта.

Семантика одинакова для всех стран — её реализует общий модуль `src/common/overrides.py`. Для Украины это поправка поверх собранных данных, для Армении и Азербайджана — единственный источник значений, поэтому у них `"enabled": true` обязателен: без него запуск обрывается, а не публикует пустой файл.

### Когда

* **Поставщика нет на сайте-источнике.** Основной сценарий — отопление КП «Київтеплоенерго».
* **Источник сломался или отдаёт мусор.** В Telegram пришло «тарифы не обновлены — не пройдена валидация», а цифра нужна сейчас.
* **Тариф изменился между запусками.** Крон работает 25-го числа, а поправить надо сегодня.
* **Источник врёт.** Скрипт нашёл расхождение через Search Grounding, вы проверили и знаете правильное значение.

### Как это применяется

1. Скрипт скачивает и парсит все источники как обычно.
2. Поверх результата накладываются значения из `manual_override`.
3. Отдельно и независимо отрабатывает сверка через Gemini Search Grounding, отчёт уходит в Telegram.
4. Файл сохраняется.

Ключевое: **переопределения не отключают ни скрейпинг, ни AI-сверку.** Можно спокойно держать `enabled: true` постоянно ради одного зафиксированного города — остальное продолжит обновляться само.

`"enabled": false` полностью выключает весь блок, при этом настройки внутри сохраняются — удобно, чтобы не терять заготовки.

### Что означают поля

#### Блок `manual_override.electricity`

| Поле | Что это | Пример значения |
|---|---|---|
| `source_url` | Ссылка на сайт, откуда взята цифра. Никак не влияет на расчёты, попадает в JSON и нужна, чтобы через полгода вспомнить, откуда данные. | `"https://www.kmu.gov.ua/npas/..."` |
| `base_rate` | **Цена 1 кВт·ч в гривнах с НДС для однозонного счётчика.** Это единственное число, от которого зависят все остальные тарифы на электричество. | `4.32` — значит 1 кВт·ч стоит 4 грн 32 коп. |
| `effective_date` | С какого числа тариф действует. Формат строго `YYYY-MM-DD`. Приложение показывает эту дату пользователю и по ней же скрипт понимает, не появился ли где-то тариф посвежее. | `"2024-06-01"` |
| `decree_info` | **Текстовая подпись «на основании чего действует тариф».** Свободная строка, никем не парсится, показывается в приложении мелким шрифтом под цифрой, чтобы пользователь видел, что цифра не с потолка. | `"Постанова КМУ № 632 від 31.05.2024"` |

> 💡 **Про `base_rate` и зоны.** В JSON кроме `base_rate` лежат тарифы для двухзонных и трёхзонных счётчиков (`zones.two_zone.night.rate` и т. д.). Их **не надо** прописывать руками: у каждой зоны есть свой коэффициент (ночь — 0.5, пик — 1.5 и так далее), и скрипт сам пересчитает все зоны, как только вы переопределите `base_rate`. Написали `base_rate: 5.00` — ночной тариф автоматически станет `2.50`, пиковый `7.50`.

#### Блоки `manual_override.water` / `.hot_water` / `.heating`

| Поле | Что это |
|---|---|
| `source_url` | Ссылка на источник для всего блока целиком (для всех городов сразу). |
| `cities` | Объект, где **ключ — это `city_code`**, а значение — набор полей, которые надо подменить у этого города. |

Поля внутри `cities.<city_code>` — те же, что в самом JSON (полное описание в [docs/ru/JSON_SPECIFICATION.md](docs/ru/JSON_SPECIFICATION.md)):

| Блок | Поля | Смысл цифр |
|---|---|---|
| `water` | `city_name`, `supplier`, `water_supply`, `sewage`, `total_rate`, `unit`, `effective_date`, `decree_info` | `water_supply` — грн за 1 м³ холодной воды, `sewage` — грн за 1 м³ водоотведения, `total_rate` — их сумма. Если услуги нет, ставьте `0.0`. |
| `hot_water` | `city_name`, `supplier`, `rate`, `unit`, `effective_date`, `decree_info` | `rate` — грн за 1 м³ горячей воды с НДС. |
| `heating` | `city_name`, `supplier`, `tariff_type`, `rate_gcal`, `rate_gcal_hour`, `unit`, `effective_date`, `decree_info` | `tariff_type` — `"one_rate"` или `"two_rate"`. `rate_gcal` — грн за 1 Гкал. `rate_gcal_hour` — абонплата за подключённую нагрузку, только у двухставковых; у одноставковых ставьте `0.0`. |

`supplier` — название предприятия, `city_name` — название города для показа в приложении, `unit` — единица измерения (`"m3"` для воды и ГВ, `"Gcal"` для отопления), `effective_date` и `decree_info` — то же самое, что у электричества.

### Как добавить город, которого нет в источнике

Если `city_code` **уже есть** в собранных данных — город патчится: подменяются только перечисленные поля, остальные остаются как были. Если такого `city_code` **нет** — город дописывается в список, но для этого нужно указать **все** поля из таблицы выше. Не хватает хотя бы одного — запись пропускается, а в Telegram уходит список недостающих полей.

`city_code` для нового города вы выбираете сами. Берите тот же код, что у этого города в блоке `water`, если поставщик в городе один — так приложению будет проще связать услуги.

### Примеры на живых задачах

#### Пример 1. Поднялся тариф на электричество, а крон будет только 25-го

Меняется одна цифра — зоны пересчитаются сами:

```json
"electricity": {
  "source_url": "https://www.kmu.gov.ua/npas/pro-zminu-tarifiv",
  "base_rate": 5.10,
  "effective_date": "2026-09-01",
  "decree_info": "Постанова КМУ № 1024 від 20.08.2026"
}
```

После запуска в JSON будет `base_rate: 5.1`, `zones.two_zone.night.rate: 2.55`, `zones.three_zone.peak.rate: 7.65` — вручную их прописывать не нужно.

#### Пример 2. Поставщика вообще нет на сайте-источнике

Это случай КП «Київтеплоенерго» с отоплением. Города `kyiv` в блоке `heating` не существует, поэтому перечисляем **все** поля — иначе запись будет пропущена:

```json
"heating": {
  "source_url": null,
  "cities": {
    "kyiv": {
      "city_name": "Київ",
      "supplier": "КП \"КИЇВТЕПЛОЕНЕРГО\"",
      "tariff_type": "one_rate",
      "rate_gcal": 1654.41,
      "rate_gcal_hour": 0.0,
      "unit": "Gcal",
      "effective_date": "2022-10-01",
      "decree_info": "Розпорядження КМВА № 673 від 30.09.2022, тариф для населення на період воєнного стану"
    }
  }
}
```

#### Пример 3. Подправить одну цифру у города, который уже есть

Город `lviv` в горячей воде парсится с источника, но вы знаете, что тариф изменился. Достаточно трёх полей — `city_name`, `supplier` и `unit` останутся теми, что пришли с сайта:

```json
"hot_water": {
  "source_url": null,
  "cities": {
    "lviv": {
      "rate": 118.40,
      "effective_date": "2026-07-01",
      "decree_info": "Рішення виконкому Львівської міської ради № 512 від 20.06.2026"
    }
  }
}
```

#### Пример 4. Двухставковый тариф на отопление

У Львова, Вінниці, Полтави, Черкас и Івано-Франківська тариф состоит из двух частей. `rate_gcal` — то, что умножается на потреблённые Гкал, `rate_gcal_hour` — абонплата за подключённую нагрузку дома:

```json
"heating": {
  "cities": {
    "lviv": {
      "tariff_type": "two_rate",
      "rate_gcal": 1363.44,
      "rate_gcal_hour": 104998.81,
      "effective_date": "2021-02-01",
      "decree_info": "Тариф НКРЕКП, чинний станом на 01.02.2021"
    }
  }
}
```

#### Пример 5. Как ничего не переопределять

Заготовка со всеми полями `null` — рабочая конфигурация, которая не меняет ничего. `null` означает «не трогай это поле», поэтому такой блок можно держать в файле постоянно:

```json
"electricity": {
  "source_url": null,
  "base_rate": null,
  "effective_date": null,
  "decree_info": null
}
```

### Ловушки

* **`null` — это «не переопределять».** Поле со значением `null` игнорируется. Чтобы обнулить тариф, пишите `0.0`, а не `null`.
* **`city_code` должен совпадать посимвольно.** Загляните в `config/ua/city_registry.json` или в текущий `docs/tariffs_ua.json`, прежде чем писать код руками. Опечатка не вызовет ошибку — она молча создаст новый город (или отвалится по неполноте полей).
* **Разовую правку надо снимать.** Если вы зафиксировали цифру «пока источник лежит», не забудьте потом убрать её из `cities`, иначе она будет вечно перекрывать реальные данные.
* **Отопление КТЕ надо перепроверять раз в сезон.** Значение `1654.41` взято с [kte.kmda.gov.ua/tarufu](https://kte.kmda.gov.ua/tarufu/), где оно опубликовано картинкой. Мораторий на повышение действует весь военный период, но при его отмене цифру надо будет обновить руками.

### Полный пример

```json
"manual_override": {
  "enabled": true,
  "electricity": {
    "source_url": null,
    "base_rate": null,
    "effective_date": null,
    "decree_info": null
  },
  "water": {
    "source_url": null,
    "cities": {}
  },
  "hot_water": {
    "source_url": null,
    "cities": {}
  },
  "heating": {
    "source_url": null,
    "cities": {
      "kyiv": {
        "city_name": "Київ",
        "supplier": "КП \"КИЇВТЕПЛОЕНЕРГО\"",
        "tariff_type": "one_rate",
        "rate_gcal": 1654.41,
        "rate_gcal_hour": 0.0,
        "unit": "Gcal",
        "effective_date": "2022-10-01",
        "decree_info": "Розпорядження КМВА № 673 від 30.09.2022, тариф для населення на період воєнного стану"
      }
    }
  }
}
```

Здесь единственное реальное переопределение — отопление по Киеву, которого нет ни в одном сводном источнике. Остальные блоки оставлены заготовками с `null`, чтобы не искать структуру в документации, когда понадобится быстро что-то зафиксировать.

> ⚠️ **Что нужно поменять в приложении после добавления горячей воды и отопления:** блоки `electricity` и `water` не изменились ни на байт, но в корне JSON появились два новых ключа — `hot_water` и `heating`. Для `kotlinx.serialization` это значит, что парсер должен быть создан как `Json { ignoreUnknownKeys = true }`, иначе он бросит `SerializationException`. Если флаг уже стоит (или используется Moshi/Gson — они игнорируют неизвестные ключи по умолчанию), менять в приложении не нужно вообще ничего. Новые DTO понадобятся только когда захотите показывать ГВ и ЦО.

### Краткая сводка по интеграции:
1. **Локальный кэш (Offline Fallback):** Положите стартовые `assets/tariffs_<код>_default.json` в локальные `assets/tariffs/` Android-приложения на случай отсутствия интернета.
2. **Удаленное обновление (Remote Sync):** При наличии интернета выкачивайте обновленный файл по любому из доступных URL:
   * **Cloudflare / R2 CDN:** `https://tarrifs.foleks.com/<код>/tariffs_<код>.json`
   * **GitHub Pages:** `https://alxpanther.github.io/communal_tarrifs/tariffs_<код>.json`
3. **Индекс стран:** `https://tarrifs.foleks.com/tariffs_index.json` и `https://alxpanther.github.io/communal_tarrifs/tariffs_index.json`. У каждого хоста своя копия со своими значениями `path`, потому что раскладка файлов на хостах разная.
4. **Парсинг и Модели:** Для быстрого создания моделей данных в Android используйте Kotlin DTO из [docs/ru/JSON_SPECIFICATION.md](docs/ru/JSON_SPECIFICATION.md#3-готовые-kotlin-data-classes-kotlinxserialization).
