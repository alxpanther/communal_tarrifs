## 1. Что изменилось в JSON

В корне файла появились **два новых блока**: `hot_water` и `heating`.

```jsonc
{
  "version": "1.0",
  "last_updated_at": "...",
  "country": "UA",
  "currency": "UAH",
  "electricity": { ... },   // НЕ ИЗМЕНИЛСЯ
  "water":       { ... },   // НЕ ИЗМЕНИЛСЯ
  "hot_water":   { ... },   // НОВЫЙ
  "heating":     { ... }    // НОВЫЙ
}
```

**Блоки `electricity` и `water` не менялись ни на байт** — ни одно поле не переименовано, не удалено и не поменяло тип. Весь существующий код, который читает электричество и холодную воду, продолжает работать без единой правки.

## 2. Обязательный минимум (без этого приложение упадёт)

Если JSON парсится через `kotlinx.serialization`, парсер обязан игнорировать неизвестные корневые ключи:

```kotlin
val json = Json { ignoreUnknownKeys = true }
```

Без этого флага `Json.decodeFromString<TariffResponse>(...)` бросит `SerializationException: Encountered an unknown key 'hot_water'`, и приложение перестанет читать тарифы **вообще, включая старые блоки**.

* Если флаг уже стоит — делать не нужно ничего, приложение продолжит работать как раньше и просто не будет показывать новые услуги.
* Если используется Moshi или Gson — они игнорируют неизвестные ключи по умолчанию, тоже ничего не нужно.

**Это первое, что надо найти и проверить в проекте приложения.**

## 3. Модели данных

Готовые DTO лежат в [JSON_SPECIFICATION.md, раздел 3](JSON_SPECIFICATION.md#-3-готовые-kotlin-data-classes-kotlinxserialization). Ключевые моменты:

```kotlin
@Serializable
data class TariffResponse(
    // ... существующие поля без изменений ...
    @SerialName("hot_water") val hotWater: HotWaterTariff? = null,
    @SerialName("heating")   val heating:  HeatingTariff?  = null
)
```

**Оба поля обязаны быть nullable со значением по умолчанию.** Причина: в кэше у пользователя (Room / DataStore / файл в `filesDir`) может лежать скачанный раньше JSON без этих блоков. Если объявить их non-null, приложение упадёт при чтении собственного кэша после обновления.

Структура блоков зеркалит уже существующий `water`:

| Блок | Элемент списка | Тариф |
|---|---|---|
| `hot_water` | `CityHotWaterTariff` | `rate: Double` — грн за 1 м³ с НДС |
| `heating` | `CityHeatingTariff` | `rateGcal: Double` — грн за 1 Гкал; `rateGcalHour: Double` — абонплата, `0.0` у одноставковых; `tariffType: String` — `"one_rate"` / `"two_rate"` |

## 4. Расчёты

Формулы с выкладками — в [JSON_SPECIFICATION.md, разделы 4.3 и 4.4](JSON_SPECIFICATION.md#43-расчет-стоимости-горячей-воды). Коротко:

**Горячая вода** (счётчик в м³, ровно как холодная):

```kotlin
val sum = deltaCubicMeters * city.rate
```

**Отопление** (счётчик в Гкал):

```kotlin
val sum = deltaGcal * city.rateGcal
```

Для `tariffType == "two_rate"` формально есть ещё постоянная часть — `rateGcalHour`, умноженная на подключённую тепловую нагрузку дома в Гкал/год. **Жилец эту величину не знает** и в приложении её взять неоткуда, поэтому:

* считать по `rateGcal`;
* `rateGcalHour` либо не показывать вообще, либо показывать справочно с подписью «абонплата за підключене навантаження, нараховується постачальником».

Не пытайтесь угадать нагрузку или спросить её у пользователя — он не найдёт эту цифру в квитанции в понятном виде.

## 5. Четыре подводных камня — прочитать до того, как писать код

### 5.1. Списки городов в трёх блоках разные

| Блок | Городов |
|---|---|
| `water` | 50 |
| `hot_water` | 18 |
| `heating` | 28 |

Причина не в неполноте сбора: сводный источник публикует только тарифы, установленные НКРЕКП, а централизованное тепло есть далеко не везде. Это нормальное состояние, оно не изменится.

**Следствие:** для выбранного пользователем города данных по отоплению может просто не быть. Приложение обязано это переживать — не показывать услугу, а не падать и не рисовать ноль.

### 5.2. `city_code` совпадает между блоками не всегда

Совпадает там, где в городе **один** поставщик тепла: `kyiv`, `lviv`, `vinnytsia`, `kharkiv`, `poltava`, `rivne`, `sumy`, `odesa`, `zaporizhzhia` и большинство остальных.

Не совпадает там, где поставщиков несколько — «чистый» код тогда не достаётся никому:

| Город | `water` | `heating` |
|---|---|---|
| Дніпро | `dnipro` | `dnipro_teploenerho`, `dnipro_komenerhoservis` |
| Миколаїв | `mykolaiv` | `mykolaiv_mykolaivoblteploenerho`, `mykolaiv_mykolaivska_teploelektrotsentral` |
| Черкаси | `cherkasy` | `cherkasy_cherkaske_khimvolokno`, `cherkasy_cherkasyteplokomunenerho` |
| Чернігів | `chernihiv` | `chernihiv_firma`, `chernihiv_oblteplokomunenerho` |

Это не баг: в этих городах разные районы обслуживают разные предприятия с разными тарифами, и выбрать за пользователя нельзя.

**Как правильно:**

* `city_code` — стабильный первичный ключ **внутри своего блока**. Хранить выбор пользователя надо отдельно для каждой услуги.
* Для связывания услуг между собой ориентироваться на `city_name`: выбрал человек Черкаси для воды — в списке отопления предложить ему обе записи с `cityName == "Черкаси"` и дать выбрать своего поставщика.
* Не делать `heating.cities.first { it.cityCode == waterCityCode }` — для четырёх городов это молча вернёт null.

Про правила назначения кодов см. [README.md → Как назначается «простой» код города](../README.md#как-назначается-простой-код-города).

### 5.3. `effective_date` в прошлом — это нормально

У большинства записей по ГВ и ЦО стоит `2021-02-01`, у Києва — `2022-10-01`. Это **не устаревшие данные**. На повышение тарифов на тепло для населения действует мораторий на весь период военного положения и шесть месяцев после него, поэтому цифры действительно заморожены с тех пор. Проверено сверкой с сайтами самих поставщиков — совпадает до копейки.

В JSON лежит **тариф, который реально платит население**. Економічно обґрунтовані тарифи (они выше в полтора-два раза и публикуются рядом на сайтах компаний) в файл не попадают.

Не надо писать в UI «тариф устарел» по дате. Если хочется что-то показать — показывайте `decree_info`, там человеческая подпись вида «Розпорядження КМВА № 673 від 30.09.2022, тариф для населення на період воєнного стану».

### 5.4. Киев в тепле — это Київтеплоенерго

`city_code == "kyiv"` в `hot_water` и `heating` — это КП «КИЇВТЕПЛОЕНЕРГО», основной поставщик города (97,89 грн/м³ и 1654,41 грн/Гкал). Второй киевский поставщик, ТОВ «Євро-Реконструкція», обслуживает часть районов и лежит под кодом `kyiv_yevro_rekonstruktsiia` (75,96 и 1408,27). Киевлянам нужно давать выбор между ними.

## 6. Чек-лист работ по приложению

- [ ] Найти создание `Json`-парсера, убедиться что стоит `ignoreUnknownKeys = true`. **Сделать в первую очередь.**
- [ ] Добавить DTO `HotWaterTariff`, `CityHotWaterTariff`, `HeatingTariff`, `CityHeatingTariff` (копируются из спецификации).
- [ ] Добавить `hotWater` и `heating` в `TariffResponse` — nullable, с `= null`.
- [ ] Расширить слой хранения (Room-сущности / DataStore) под два новых списка городов.
- [ ] Добавить два типа счётчика в доменную модель: горячая вода (м³) и отопление (Гкал).
- [ ] Экран выбора поставщика: отдельный выбор для ГВ и ЦО, не переиспользовать выбор из холодной воды (см. 5.2).
- [ ] Реализовать расчёты из раздела 4.
- [ ] Обработать «для вашего города нет данных по этой услуге» — скрывать услугу, а не показывать нули.
- [ ] Обновить `app/src/main/assets/tariffs_ua_default.json` свежей копией [assets/tariffs_ua_default.json](../assets/tariffs_ua_default.json) из этого репозитория.
- [ ] Проверить, что старый закэшированный JSON без новых блоков всё ещё читается и не роняет приложение.
- [ ] Строки в UI — только через `.arb`/`strings.xml`, хардкод названий услуг недопустим.
