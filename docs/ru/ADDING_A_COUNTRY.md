# Добавление тарифов другой страны

> **Язык:** русский — зеркало для чтения человеком.
> Каноническая версия: [../en/ADDING_A_COUNTRY.md](../en/ADDING_A_COUNTRY.md), именно её читают AI-агенты.
> Оба файла обязаны совпадать по смыслу; см. [DOCUMENTATION_RULES.md](DOCUMENTATION_RULES.md).

Эта страница — для всех, кто хочет добавить пайплайн тарифов для страны, отличной от Украины:
для владельца проекта, для контрибьютора и для AI-агента. Сначала прочитайте
[PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) и [ARCHITECTURE.md](ARCHITECTURE.md); здесь только то,
что специфично для новой страны.

---

## 1. Как обстоят дела сейчас, честно

Сегодня в репозитории **один** пайплайн — `src/tariffs_fetcher.py`, написанный под Украину, с
украинскими путями и зашитым значением `"country": "UA"`. Он работает и закоммичен как есть.

Всё, что описано ниже в разделах 2–4, — это **согласованная целевая структура для второй страны**.
Это соглашение, а не существующий код. Реализует его тот, кто первым добавит страну. Перенос
украинского пайплайна в эту структуру — отдельное изменение, которое **требует согласия владельца
проекта**, потому что от нынешних путей зависят CI-воркфлоу, Docker-файлы и опубликованные URL.

---

## 2. Целевая структура

Страна обозначается **кодом ISO 3166-1 alpha-2 в нижнем регистре** (`ua`, `pl`, `de`, `kz`).

```
config/
├── ua/
│   ├── sources.json
│   └── city_registry.json
└── pl/                          # ваша страна
    ├── sources.json             # URL источников, настройки модели, manual_override
    └── city_registry.json       # стартует как {"suppliers": {}, "heat_suppliers": {}}

src/
├── common/                      # общие, не зависящие от страны помощники
│   ├── telegram_notifier.py
│   ├── http.py                  # fetch_html и вокруг него
│   ├── registry.py              # реестр city_code: загрузка / назначение / сохранение
│   ├── llm.py                   # выбор модели Gemini, извлечение, search grounding
│   └── jsonio.py                # загрузка базовой схемы, запись обоих выходных файлов
└── countries/
    ├── ua/fetcher.py
    └── pl/fetcher.py            # ваш пайплайн: одна точка входа main(config)

assets/
├── tariffs_ua_default.json
└── tariffs_pl_default.json      # оффлайн-фоллбэк, вшиваемый в приложение

docs/
├── tariffs_ua.json              # исторический путь, сохраняется ради обратной совместимости
└── pl/
    └── tariffs_pl.json          # новые страны получают собственную папку
```

Ключ в Cloudflare R2 повторяет форму существующего: `pl/tariffs_pl.json`.

`docs/tariffs_ua.json` остаётся в корне `docs/` **навсегда**: выпущенные сборки Android скачивают
именно этот URL. Не «наводите порядок», перенося его в `docs/ua/`.

## 3. Контракт выходного файла

Ваш пайплайн обязан выдавать тот же корневой объект, что и украинский. Полное описание полей —
[JSON_SPECIFICATION.md](JSON_SPECIFICATION.md).

```jsonc
{
  "version": "1.0",
  "last_updated_at": "2026-08-20T12:00:00.000000",  // ISO 8601
  "country": "PL",                                  // ISO 3166-1 alpha-2, верхний регистр
  "currency": "PLN",                                // ISO 4217
  "electricity": { ... },
  "water":       { ... },
  "hot_water":   { ... },
  "heating":     { ... }
}
```

Правила:

1. **Имена и типы полей заморожены.** Это контракт с Android-приложением. Используйте их ровно так
   же, как Украина, включая значения `unit` (`"kWh"`, `"m3"`, `"Gcal"`) и формат даты `YYYY-MM-DD`.
2. **Категория, которой в вашей стране нет, опускается или остаётся с пустым списком `cities`.** Не
   выдумывайте значения-заглушки и не приспосабливайте существующее поле под другой смысл.
3. **Категория, которой нет в нынешней схеме** (сетевой газ, вывоз мусора, фиксированная месячная
   абонплата), требует нового блока. Это изменение схемы: **согласуйте его с владельцем проекта до
   написания кода**, потому что приложение придётся расширять синхронно.
4. **Единицы измерения и смысл ставок обязаны совпадать с описанием поля.** Если в вашей стране тепло
   считают в ГДж, а не в Гкал, не кладите молча ГДж в `rate_gcal` — поднимите вопрос об изменении
   схемы.
5. `city_code` должен быть устойчивым латинским слагом в нижнем регистре, уникальным внутри своего
   блока и назначаться детерминированной функцией — никогда языковой моделью.

## 4. Пошагово

1. **Выберите источники.** Лучше по одной официальной сводной странице на категорию (регулятор или
   национальный статистический портал). Все URL пишите в `config/<cc>/sources.json`; в код не
   попадает ничего.
2. **Создайте пустой реестр** `config/<cc>/city_registry.json` с двумя пустыми секциями.
3. **Напишите парсер.** По каждой категории решите: жёсткая таблица → регулярные выражения;
   свободная вёрстка или нерегулярная таблица → вызов LLM на извлечение. Никогда не используйте
   модель для чисел, которые можно разобрать программно.
4. **Валидируйте, прежде чем доверять.** Минимум: пределы разумности по каждой ставке, сходимость
   составляющих с напечатанной суммой, совпадение количества строк с таблицей источника, ни одна
   строка не использована дважды. Непройденная валидация обязана отклонить блок целиком и сохранить
   прежние значения — эталонная реализация это украинская `validate_water_cities()`.
5. **Текстовые поля берите из HTML источника**, а не из ответа модели: названия поставщиков, периоды,
   реквизиты постановлений.
6. **Назначайте `city_code`** через общий помощник реестра: известный поставщик → значение из
   реестра, неизвестный → детерминированная транслитерация названия города для вашего языка, затем
   дозапись в реестр и уведомление в Telegram. Скопируйте правило конкуренции для городов с
   несколькими поставщиками.
7. **Поддержите `manual_override`** с той же семантикой: `null` — «не переопределять», ключи
   городов — `city_code`, новому городу нужен полный набор полей.
8. **Подключите публикацию**: запись в `docker-compose.yml`, если это полезно, шаг или элемент
   матрицы в `.github/workflows/fetch_tariffs.yml` и ключ загрузки в R2 `<cc>/tariffs_<cc>.json`.
9. **Напишите документацию** в `docs/en/` и `docs/ru/` и добавьте новые строки в `docs/README.md` и
   `PROJECT_STRUCTURE.md`.
10. **Прогоните всё целиком минимум дважды** и убедитесь, что второй запуск выдаёт побайтово те же
    `city_code`.

## 5. То, что не обсуждается

Это инварианты, благодаря которым опубликованному файлу можно доверять. Пайплайн, нарушающий любой
из них, принят не будет.

* Сбой никогда не стирает данные. Сломанный источник, ошибка HTTP, непройденная валидация →
  сохранить прежний блок JSON и отправить алерт.
* `city_code` не меняется после назначения, а реестр коммитится в git.
* Никаких зашитых в Python URL, названий моделей и таймаутов.
* Ни один вывод языковой модели не попадает в файл без сверки с источником.
* Генерируемые файлы руками не правятся.
* Комментарии в коде — на английском; документация — и на английском, и на русском.

## 6. Чек-лист для пул-реквеста

- [ ] `config/<cc>/sources.json` со всеми используемыми URL и заготовкой `manual_override`
- [ ] `config/<cc>/city_registry.json` закоммичен (может быть пустым)
- [ ] `src/countries/<cc>/fetcher.py` с единственной точкой входа
- [ ] Общая логика используется из `src/common/`, а не скопирована
- [ ] Валидация по каждой категории, при отклонении сохраняются прежние значения
- [ ] Детерминированное назначение `city_code`, устойчивость проверена двумя запусками
- [ ] `manual_override` поддержан и описан
- [ ] Результат сверен с [JSON_SPECIFICATION.md](JSON_SPECIFICATION.md); схема не менялась, либо
      изменение схемы заранее согласовано с владельцем проекта
- [ ] Результат пишется в `docs/<cc>/tariffs_<cc>.json` и `assets/tariffs_<cc>_default.json`
- [ ] CI-воркфлоу обновлён (запуск, коммит, загрузка в R2, Pages)
- [ ] Документация добавлена в `docs/en/` **и** `docs/ru/`, индекс обновлён
- [ ] Пример сгенерированного JSON приложен к описанию пул-реквеста
