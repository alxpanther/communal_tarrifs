# Добавление тарифов другой страны

> **Язык:** русский — зеркало для чтения человеком.
> Каноническая версия: [../en/ADDING_A_COUNTRY.md](../en/ADDING_A_COUNTRY.md), именно её читают AI-агенты.
> Оба файла обязаны совпадать по смыслу; см. [DOCUMENTATION_RULES.md](DOCUMENTATION_RULES.md).

Эта страница — для всех, кто хочет добавить пайплайн тарифов ещё для одной страны: для владельца
проекта, для контрибьютора и для AI-агента. Сначала прочитайте
[PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) и [ARCHITECTURE.md](ARCHITECTURE.md); здесь только то,
что специфично для новой страны.

---

## 1. Как обстоят дела сейчас

Опубликованы три страны: Украина (`UA`), Армения (`AM`) и Азербайджан (`AZ`). Пайплайны бывают двух
видов, и новая страна будет одним из них:

* **Пайплайн со сбором данных** — Украина. Официальные сводные страницы существуют, поэтому
  `src/countries/ua/fetcher.py` качает, разбирает, валидирует и только потом сохраняет.
* **Пайплайн из конфига** — Армения и Азербайджан. Регуляторы публикуют решения текстом и в PDF, и
  разбирать там нечего, поэтому числа лежат в `config/<cc>/sources.json` в `manual_override`, а
  `src/common/manual_pipeline.py` превращает их в тот же самый JSON-файл. Собственный `fetcher.py`
  страны — это десяток строк, называющих страну.

Если нормального источника нет, начинайте с варианта «из конфига». Это полноценный поддерживаемый
пайплайн, а не заглушка: добавление стадии сбора позже ничего ниже по течению не меняет.

## 2. Раскладка

Страна определяется **кодом ISO 3166-1 alpha-2**: в данных — в верхнем регистре, в путях — в нижнем
(`ua`, `am`, `az`, `pl`).

```
config/
├── countries.json               # добавьте сюда запись — именно она публикует страну
└── pl/                          # ваша страна
    ├── sources.json             # URL источников, расписание зон, manual_override
    └── city_registry.json       # начинается как {"suppliers": {}, "heat_suppliers": {}}

src/
├── common/                      # общий код, не зависящий от страны — используйте, не копируйте
└── countries/
    └── pl/fetcher.py            # ваш пайплайн: единственная точка входа main(notifier)

assets/
└── tariffs_pl_default.json      # генерируется: оффлайн-файл, вшиваемый в приложение

docs/
└── tariffs_pl.json              # генерируется: опубликованный файл, плоско в веб-корне
```

Оба выходных файла пишет `common/jsonio.py`; сами вы их никогда не открываете.

Раскладку публикации задаёт Android-приложение, и она разная на разных хостах:

| | Cloudflare R2 | GitHub Pages |
|---|---|---|
| Файл страны | `pl/tariffs_pl.json` | `tariffs_pl.json` |
| Индекс стран | `tariffs_index.json` | `tariffs_index.json` |

`docs/` — это корень GitHub Pages, поэтому каждый файл страны лежит в `docs/` **плоско**, включая
`tariffs_ua.json`: выпущенные сборки Android ходят ровно по этим адресам. Папки по странам есть
только на R2, и обе копии индекса несут соответствующие значения `path` (см.
[JSON_SPECIFICATION.md](JSON_SPECIFICATION.md), раздел 6).

## 3. Контракт выхода

Ваш пайплайн обязан выдавать тот же корневой объект, что и остальные. Полный справочник полей —
[JSON_SPECIFICATION.md](JSON_SPECIFICATION.md).

```jsonc
{
  "version": "1.0",
  "last_updated_at": "2026-08-20T12:00:00.000000",  // ISO 8601
  "country": "PL",                                  // ISO 3166-1 alpha-2, верхний регистр
  "country_names": { "ru": "Польша", "uk": "Польща" },
  "currency": "PLN",                                // ISO 4217
  "electricity": { ... },
  "water":       { ... },
  "hot_water":   { ... },
  "heating":     { ... }
}
```

Правила:

1. **Имена и типы полей заморожены.** Это контракт с Android-приложением. Переиспользуйте их ровно
   так, как это делает Украина, включая значения `unit` (`"kWh"`, `"m3"`, `"Gcal"`) и формат даты
   `YYYY-MM-DD`.
2. **Корневые поля берутся из `config/countries.json`** через `common/jsonio.build_root()`. Никогда
   не пишите `country`, `country_names` или `currency` руками внутри пайплайна.
3. **У категории, которой в стране нет, остаётся пустой список `cities`.** В Армении нет
   централизованного отопления, поэтому её блоки `hot_water` и `heating` пусты — это правильный
   способ это сказать. Не выдумывайте числа-заглушки и не используйте существующее поле в другом
   значении.
4. **Категория, которой нет в текущей схеме** (газ, вывоз мусора, фиксированная абонплата), требует
   нового блока. Это изменение схемы: **согласуйте его с владельцем до написания кода**, потому что
   приложение придётся расширять синхронно.
5. **Единицы и смысл ставки обязаны совпадать с описанием поля.** Если в вашей стране тепло меряют
   в ГДж, а не в Гкал, не кладите молча ГДж в `rate_gcal` — поднимите вопрос о схеме.
6. `city_code` — стабильный латинский slug в нижнем регистре, уникальный внутри своего блока и
   назначенный детерминированной функцией, а не языковой моделью.

## 4. Пошагово

1. **Зарегистрируйте страну** в `config/countries.json`: `code`, `country_names` для каждого языка
   приложения, `currency`, `pipeline` (имя папки в `src/countries/`), `enabled`, `min_app_version`.
   Пока этой записи нет, ничего не публикуется.
2. **Создайте `config/<cc>/sources.json`.** Все URL, к которым вы обращаетесь, — сюда, плюс
   `settings` и каркас `manual_override`. Для страны «из конфига» заполните ещё `electricity.zones`
   расписанием зон и коэффициентами: ставки всегда выводятся как `base_rate × coefficient` и никогда
   не записываются дважды.
3. **Создайте `config/<cc>/city_registry.json`** с двумя пустыми секциями.
4. **Напишите `src/countries/<cc>/fetcher.py`** с функцией `main(notifier)`.
   * Источника для разбора нет → вызовите `common.manual_pipeline.run(country, notifier)` и всё.
     Fetcher Армении целиком является шаблоном.
   * Источник есть → для каждой категории решите: жёсткая таблица → регулярные выражения;
     свободная страница или нерегулярная таблица → вызов LLM. Никогда не спрашивайте модель о
     числах, которые можно разобрать кодом.
5. **Проверяйте, прежде чем доверять.** Минимум: потолки разумности по каждой ставке, сходимость
   компонентов с напечатанной суммой, совпадение числа строк с таблицей-источником, ни одна строка
   источника не использована дважды. Провал проверки обязан отвергнуть блок целиком и сохранить
   прежние значения — образец реализации: украинская `validate_water_cities()`.
6. **Текстовые поля берите из HTML источника**, а не из ответа модели: названия поставщиков, периоды,
   реквизиты решений.
7. **Назначайте `city_code`** через `common/registry.py`: зарегистрированный поставщик сохраняет свой
   код, неизвестный дописывается и уходит в Telegram. Для пайплайна со сбором добавьте
   детерминированную транслитерацию для своего языка и правило конкуренции для городов с несколькими
   поставщиками.
8. **Доставку настраивать не нужно.** `src/run_country.py` подхватывает страну из
   `config/countries.json`, а CI-workflow выводит список загрузок в R2 из сгенерированного индекса.
   `docker-compose.yml` правьте только если пользуетесь локальным контейнером деплоя.
9. **Напишите документацию** в `docs/en/` и `docs/ru/` и обновите `docs/README.md` и
   `PROJECT_STRUCTURE.md`.
10. **Прогоните всё от начала до конца минимум дважды** — `python src/run_country.py <cc>` — и
    убедитесь, что второй запуск даёт побайтово те же `city_code`.

## 5. Не обсуждается

Это инварианты, благодаря которым опубликованному файлу можно верить. Пайплайн, нарушающий любой из
них, не будет принят.

* Сбой никогда не стирает данные. Сломанный источник, ошибка HTTP, провал валидации → оставляем
  предыдущий блок JSON и шлём алерт.
* Сбой одной страны никогда не останавливает остальные и не убирает её из индекса.
* Назначенный `city_code` не меняется никогда, а реестр коммитится в git.
* Никаких зашитых в Python URL, имён моделей, таймаутов, значений тарифов и названий стран.
* Ни один вывод языковой модели не попадает в файл без сверки с источником.
* Генерируемые файлы руками не правятся.
* Комментарии в коде — по-английски, документация — и по-английски, и по-русски.

## Какой пайплайн получает новая страна

**Страна добавляется тем, что пайплайн учат читать её источники, а не тем, что её тарифы вписывают
в конфиг.** Ради этого правила репозиторий и существует, см. жёсткие правила в `CLAUDE.md`. Страна,
числа которой введены руками, не добавлена, а подделана, и подделка проходит любые проверки, пока
тарифы не поменяются.

Пайплайн выбирается по тому, что публикует регулятор этой страны:

| Если у страны есть… | Берём | Пример |
|---|---|---|
| одна страница со всеми городами | фетчер страны по образцу `src/countries/ua/fetcher.py` | Украина, minfin |
| отдельный источник у каждого города | `src/common/ai_pipeline.py` и секцию `cities` в конфиге | Россия |

Второй случай — обычный, и нового кода на Python он не требует вовсе: фетчер — это десять строк,
называющих страну и передающих работу дальше, а всё остальное лежит в `config/<cc>/sources.json`.

### Как завести страну на сборе по городам

1. `config/countries.json` — код, названия, валюта, `pipeline`, `enabled`.
2. `config/<cc>/sources.json`:
   * `settings` — таймаут загрузки и `settings.llm`: какой провайдер и какая модель читают
     источники (см. ARCHITECTURE, раздел 8a);
   * `validation` — потолки и `max_change_ratio` для валюты этой страны. Рублёвый потолок бессмыслен
     для тенге; ставьте их по тому, как выглядит настоящий тариф;
   * `electricity` — расписание зон, коэффициенты и `source`, если он есть;
   * `cities` — у каждого города `city_name` и по каждому блоку `urls`, `supplier`, при
     необходимости `supplier_aka` и `hint`;
   * `manual_override` — присутствует, но пустой.
3. `src/countries/<cc>/fetcher.py` — копия `src/countries/ru/fetcher.py` с заменённым кодом страны.
4. Проверять город за городом через `src/run_city.py` — по умолчанию без записи — и править
   список источников, пока каждый город не пройдёт. Только после этого собирать всю страну, и
   только с согласия владельца проекта: каждый город — это платный вызов модели.
   Первому прогону страны нужен уже опубликованный файл, поверх которого он работает: создайте его,
   прогнав страну один раз через `manual_pipeline` с пустым переопределением, либо закоммитив
   каркасный файл.
5. Документация в `docs/en/` и `docs/ru/` одновременно.

### Как выбирать источники

* Сначала само постановление регулятора, потом тарифная страница поставщика, потом расчётный центр,
  перепечатывающий постановления целиком. Новостные статьи не годятся: они пересказывают и не
  переиздаются, когда тариф меняется.
* У блока может быть несколько ссылок, и все они уходят в модель вместе — этим и пользуйтесь, когда
  тариф разнесён по документам, как это обычно бывает у двухкомпонентной горячей воды.
* PDF работает, включая сканы без текстового слоя.
* Проверяйте ссылку с той машины, где пайплайн будет работать. Некоторые региональные сайты отвечают
  браузеру и отказывают дата-центру, а некоторые не отвечают из-за границы вовсе.
